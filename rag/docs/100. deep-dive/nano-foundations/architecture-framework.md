# 아키텍처 프레임워크(Architecture Framework)

> 정독: 0회

## 1. 이 기술이 무엇인가

아키텍처 프레임워크는:

> 복잡한 시스템을 설계하고 분석하기 위한 **표준화된 구조와 관점(View), 절차(Methodology), 규칙을 제공하는 설계 체계**

**핵심 목적:**

- 시스템 구조를 일관되게 정의하고
- 이해관계자 간 해석 차이를 줄이며
- 대규모 시스템 복잡성을 통제하는 것

프레임워크 자체가 실행되는 소프트웨어는 아닙니다. 오히려:

- 무엇을 설계해야 하는지
- 어떤 관점으로 봐야 하는지
- 어떤 산출물이 필요한지

를 정의하는 **상위 수준의 설계 체계**입니다.

---

## 2. 시스템 어디에서 등장하는가

아키텍처 프레임워크는 대규모 시스템 설계 전반에서 등장합니다.

| 영역 | 활용 목적 |
|------|----------|
| 엔터프라이즈 시스템 | 조직 전체 구조 정렬 |
| 클라우드 플랫폼 | 인프라 표준화 |
| 분산 시스템 | 서비스 관계 정의 |
| 정부/금융 시스템 | 규제 및 거버넌스 |
| Kubernetes 플랫폼 | 운영 모델 표준화 |
| SRE 플랫폼 | 운영 흐름 정의 |

특히 조직 규모가 크고, 서비스 수가 많고, 운영 주체가 여러 팀인 경우 필수적으로 등장합니다.

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

아키텍처 프레임워크는 직접 하드웨어를 제어하지는 않습니다. 하지만 시스템 구조를 결정하기 때문에 결과적으로 **모든 자원 사용 방식에 영향**을 줍니다.

### CPU

동시성 구조, 서비스 분리 방식, 스케줄링 구조를 통해 CPU 사용 패턴이 달라집니다.

### Memory

캐시 전략, 객체 생명주기, 데이터 공유 모델 등에 영향을 줍니다.

### Network

특히 영향이 큽니다. Monolith vs Microservices, Sync vs Async, Event-Driven 구조에 따라 네트워크 호출량이 완전히 달라집니다.

### Disk

저장 구조, 로그 정책, 트랜잭션 전략, 데이터 일관성 모델에 영향을 줍니다.

## 4. 왜 중요한가

복잡한 시스템은 **"코드"** 보다 **"구조"** 가 장기 안정성을 결정합니다.

| 이유 | 설명 |
|------|------|
| 표준화 | 팀 간 구조 일관성 |
| 복잡성 통제 | 큰 시스템 분해 가능 |
| 운영 안정성 | 예측 가능한 구조 |
| 의사소통 | 공통 언어 제공 |
| 확장성 | 구조적 성장 가능 |
| 거버넌스 | 정책 적용 가능 |

프레임워크가 없으면 설계 기준 불일치, 서비스 구조 혼란, 중복 구현, 운영 불가능 상태가 발생하기 쉽습니다.

---

## 5. 실제 장애와 어떤 관련이 있는가

아키텍처 프레임워크 부재는 장기적으로 운영 장애를 유발합니다.

| 문제 | 원인 |
|------|------|
| 서비스 구조 붕괴 | 설계 표준 부재 |
| 장애 전파 | 의존성 통제 실패 |
| 운영 난이도 폭증 | 관점(View) 부재 |
| 팀 간 충돌 | 용어/구조 불일치 |
| 배포 혼란 | 표준 프로세스 부재 |
| 확장 실패 | 구조적 한계 |

대규모 시스템에서는 **"코드 품질"** 보다 **"아키텍처 질서"** 가 더 중요해지는 시점이 옵니다.

## 6. 핵심 메커니즘

### (1) View(관점) 분리

복잡한 시스템을 한 번에 보지 않고 관점별로 분리합니다.

| View | 의미 |
|------|------|
| Logical View | 기능 구조 |
| Runtime View | 실행 흐름 |
| Deployment View | 물리 배치 |
| Data View | 데이터 흐름 |
| Security View | 권한 구조 |

이 분리가 없으면 대규모 시스템은 분석 불가능해집니다.

### (2) Meta-model

프레임워크는 **"무엇을 설계 요소로 인정할 것인가"** 를 정의합니다.

표준 개념으로 정의되는 요소들: 서비스, 컴포넌트, 데이터 흐름, API, 메시지, 이벤트

즉, **설계 언어 자체를 규격화**합니다.

### (3) Dependency 구조 정의

아키텍처 프레임워크는 컴포넌트 간 의존 방향과 규칙을 정의합니다.

- 어떤 계층이 어떤 계층을 호출 가능한가
- 어떤 서비스가 어떤 데이터에 접근 가능한가
- 어떤 API가 외부 공개 가능한가

이 규칙이 시스템 질서를 유지합니다.

### (4) Runtime 구조 연결

프레임워크는 단순 문서가 아닙니다. 실제 런타임 구조와 연결됩니다.

- 프로세스 분리
- Pod 구조
- 네트워크 흐름
- 메시지 토폴로지
- 장애 격리

> 아키텍처 프레임워크는 결국 **운영 구조를 결정**합니다.

### (5) Governance

대규모 시스템에서는 설계 자유보다 **설계 통제**가 중요합니다.

프레임워크는 다음과 같은 거버넌스 기준이 됩니다:

- 코드 규칙
- 배포 정책
- 보안 정책
- 운영 정책
- 변경 정책

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

직접 프레임워크가 보이지는 않지만 런타임 구조에서 드러납니다.

| 관측 대상 | 의미 |
|----------|------|
| Process Tree | 실행 구조 |
| Network Socket | 서비스 연결 |
| File Layout | 배포 구조 |
| cgroup | 자원 정책 |

### Runtime

| 영역 | 관측 |
|------|------|
| Thread Model | 실행 아키텍처 |
| Heap Structure | 메모리 구조 |
| Trace Flow | 호출 구조 |
| Queue Topology | 메시지 흐름 |

### Kubernetes

Kubernetes는 사실상 **런타임 아키텍처 프레임워크의 실행 플랫폼**입니다.

| 대상 | 의미 |
|------|------|
| Namespace | 논리 격리 |
| Deployment | 배포 구조 |
| Service | 네트워크 구조 |
| Ingress/Gateway | 진입 구조 |
| HPA | 확장 정책 |
| NetworkPolicy | 통신 규칙 |
| Service Mesh | 의존성 흐름 |
