# 소프트웨어 아키텍처 (Software Architecture)

> 정독: 0회

## 1. 이 기술이 무엇인가

소프트웨어 아키텍처는:

> 소프트웨어 시스템의 전체 구조, 컴포넌트 분리 방식, 데이터 흐름, 실행 경계, 통신 방식, 자원 사용 전략을 정의하는 **상위 구조 설계**

### 핵심 목적

- 복잡성 제어
- 변경 영향 최소화
- 장애 전파 차단
- 성능 / 확장성 확보
- 운영 안정성 확보

### 핵심 관점

"코드를 어떻게 나눌 것인가"가 아니라:

- **시스템을 어떤 실행 구조로 운영할 것인가**
- **CPU / 메모리 / 네트워크 / I/O 자원을 어떻게 조직할 것인가**

를 결정하는 시스템 수준 설계입니다.

---

## 2. 시스템 어디에서 등장하는가

소프트웨어 아키텍처는 거의 모든 계층에서 등장합니다.

| 계층 | 아키텍처 역할 |
|---|---|
| **애플리케이션** | 모듈 구조, 서비스 분리 |
| **런타임** | 객체 배치, 스레드 모델 |
| **OS** | 프로세스 및 IPC 구조 |
| **네트워크** | 서비스 통신 구조 |
| **데이터베이스** | 트랜잭션 및 데이터 흐름 |
| **Kubernetes** | 배포 및 스케일 구조 |
| **운영** | 장애 격리 및 관측 구조 |

### 대표적인 아키텍처 형태

Monolith, Layered Architecture, Microservices, Event-Driven, Actor Model, CQRS, Hexagonal, Reactive Architecture

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

소프트웨어 아키텍처는 **모든 시스템 자원 사용 방식에 직접 영향**을 줍니다.

| 자원 | 영향 항목 |
|---|---|
| **CPU** | 스레드 모델, 동시성 구조 |
| **Memory** | 객체 생명주기, 캐시 구조 |
| **Network** | 서비스 호출 패턴 |
| **Disk** | 데이터 저장 및 트랜잭션 구조 |

**구조적 예시:**

- 동기 호출 과다 → CPU 대기 증가
- 객체 생성 과다 → GC 압박
- 마이크로서비스 과분리 → 네트워크 병목
- 잘못된 캐시 구조 → 메모리 폭증

---

## 4. 왜 중요한가

아키텍처는 시스템의 장애 특성, 성능 한계, 운영 난이도, 확장 가능성, 유지보수 비용을 결정합니다.

### 잘못된 아키텍처의 대표 증상

| 문제 | 원인 |
|---|---|
| **장애 전파** | 강한 결합 |
| **느린 응답** | 블로킹 구조 |
| **메모리 폭증** | 객체 생명주기 관리 실패 |
| **배포 어려움** | 의존성 얽힘 |
| **스케일 실패** | 상태 공유 구조 |
| **장애 분석 어려움** | 관측 불가능 구조 |

> 운영 단계에서 발생하는 대부분의 구조적 문제는  
> **아키텍처 결정에서 시작됩니다.**

---

## 5. 실제 장애와 어떤 관련이 있는가

실제 운영 장애는 종종 코드 한 줄보다 **아키텍처 문제**에서 발생합니다.

| 장애 | 구조적 원인 |
|---|---|
| **Cascading Failure** | 동기 의존 구조 |
| **DB 병목** | 중앙 집중 구조 |
| **Thread Pool 고갈** | 블로킹 호출 |
| **GC Stop-the-world 증가** | 객체 생성 과다 |
| **Retry Storm** | 재시도 설계 실패 |
| **Split Brain** | 분산 상태 관리 실패 |

> 특히 대규모 시스템에서는  
> "코드 오류"보다 **"구조 설계 오류"가 더 위험합니다.**

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

### (1) 컴포넌트 분리 (Component Separation)

책임 분리, 의존성 방향 통제, 변경 범위 최소화.

대표 방식: Layer, Service, Module, Domain

> 목표: "한 부분의 변경이 전체 시스템으로 전파되지 않게 만드는 것"

### (2) 실행 모델 (Execution Model)

| 모델 | 특징 |
|---|---|
| **동기 (Synchronous)** | 단순하지만 대기 발생 |
| **비동기 (Asynchronous)** | 확장성 증가 |
| **이벤트 기반 (Event-driven)** | 느슨한 결합 |
| **스트림 기반 (Stream Processing)** | 연속 처리 최적화 |

이 구조가 Thread 사용량, Queue 길이, CPU 점유율, Latency를 결정합니다.

### (3) 상태 관리 (State Management)

관리 대상: 메모리 상태, 세션 상태, 캐시 상태, 트랜잭션 상태, 분산 상태

잘못된 상태 설계는 Race Condition, Deadlock, Memory Leak, 데이터 불일치를 유발합니다.

### (4) 경계 (Boundary) 설계

아키텍처는 다음 경계를 정의합니다.

- 프로세스 경계 / 네트워크 경계
- 트랜잭션 경계 / 보안 경계
- 장애 격리 경계

좋은 아키텍처는 장애를 **"국소화"** 합니다.

### (5) 런타임 구조 (Runtime Topology)

설계는 런타임에서 실제 자원 구조로 변환됩니다.

Thread Pool, Event Loop, Heap Layout, Connection Pool, IPC Channel, Queue, File Descriptor

> 아키텍처는 단순 UML 그림이 아니라  
> **실제 운영 자원 배치 구조**입니다.

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 영역 | 관측 |
|---|---|
| `ps` / `top` / `htop` | 프로세스 구조 |
| `vmstat` | 메모리 압박 |
| `iostat` | 디스크 병목 |
| `ss` / `netstat` | 네트워크 연결 구조 |
| `perf` | CPU 병목 |
| `lsof` | 파일 디스크립터 구조 |

### Runtime

| 영역 | 관측 |
|---|---|
| Heap Dump | 객체 구조 |
| Thread Dump | 실행 흐름 |
| GC Log | 메모리 구조 문제 |
| Async Queue | 비동기 처리 상태 |
| Lock 상태 | 동기화 문제 |

### Kubernetes

| 영역 | 관측 |
|---|---|
| Pod 구조 | 실행 단위 |
| Service Mesh | 서비스 호출 구조 |
| HPA | 스케일 전략 |
| Resource Limit | 자원 격리 |
| Readiness / Liveness | 상태 관리 |
| NetworkPolicy | 경계 제어 |

> 특히 Kubernetes는  
> **"아키텍처를 실제 인프라 토폴로지로 투영하는 계층"** 입니다.
