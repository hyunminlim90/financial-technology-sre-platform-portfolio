# 소프트웨어 검증 및 확인 (Software Verification and Validation, V&V)

> 정독: 0회

## 1. 이 기술이 무엇인가

소프트웨어 검증 및 확인(V&V)은:

> 시스템이 **설계 및 구현 규칙에 맞게 정확히 만들어졌는지** **실제 요구사항과 운영 목적을 충족하는지** 를 평가하는 **품질 보증 및 신뢰성 확보 체계**

### 핵심 차이

| 구분 | 질문 | 목적 |
|---|---|---|
| **Verification** | "정확하게 구현했는가?" | 구현 무결성 검증 |
| **Validation** | "원하는 시스템을 만든 것이 맞는가?" | 요구사항 충족 확인 |

> V&V는 단순 테스트만 의미하지 않습니다.  
> 설계, 코드, 빌드, 런타임, 운영 환경까지 포함한  
> **전체 시스템 신뢰성 검증 절차**입니다.

---

## 2. 시스템 어디에서 등장하는가

V&V는 소프트웨어 생명주기 전체에서 등장합니다.

| 단계 | 수행 내용 |
|---|---|
| **요구사항** | 요구사항 충돌 / 누락 검증 |
| **아키텍처 설계** | 구조적 안정성 검증 |
| **구현** | 정적 분석, 타입 검사 |
| **빌드** | 컴파일 및 의존성 검증 |
| **테스트** | 기능 / 통합 / 성능 테스트 |
| **배포** | 환경 일관성 검증 |
| **운영** | 장애 탐지, 모니터링, 회귀 검증 |

특히 현대 시스템에서는 CI/CD, 컨테이너, Kubernetes, 분산 트랜잭션, 비동기 메시징 환경 때문에 **런타임 검증 중요성이 매우 커졌습니다.**

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

| 자원 | 영향 항목 |
|---|---|
| **CPU** | 테스트 실행, 정적 분석, fuzzing |
| **Memory** | 대규모 테스트 데이터, 런타임 상태 검증 |
| **Network** | API 통합 테스트, 분산 시스템 검증 |
| **Disk** | 로그, 테스트 결과, 데이터 무결성 확인 |

특히 다음 환경에서 영향이 큽니다.

- 대규모 통합 테스트
- 부하 테스트
- 장애 복구 시뮬레이션
- 데이터베이스 일관성 검증
- CI 병렬 빌드 환경

---

## 4. 왜 중요한가

V&V가 없으면 다음 문제가 발생합니다.

- 데이터 손상 / 트랜잭션 불일치
- 경쟁 상태 (Race Condition)
- 메모리 누수
- 장애 복구 실패
- 배포 후 시스템 붕괴
- 운영 환경과 테스트 환경의 불일치

특히 금융 / 결제 / SRE 시스템에서는 중복 결제, 메시지 유실, 부분 성공 상태, 롤백 실패, 장애 전파 같은 치명적 문제를 방지하기 위해 **필수**입니다.

---

## 5. 실제 장애와 어떤 관련이 있는가

실제 운영 장애 상당수는 **V&V 부족**에서 발생합니다.

| 문제 | 원인 |
|---|---|
| **운영에서만 장애 발생** | 테스트 환경 불일치 |
| **Deadlock** | 동시성 검증 부족 |
| **Memory Leak** | 장시간 런타임 검증 부족 |
| **데이터 정합성 오류** | 트랜잭션 검증 부족 |
| **장애 복구 실패** | Failover 검증 미실시 |
| **Kubernetes 재시작 루프** | Liveness / Readiness 검증 부족 |

특히 "단위 테스트는 통과했는데 운영에서 터지는" 문제는 대부분 통합 검증 부족, 분산 환경 검증 부족, 비동기 흐름 검증 부족에서 발생합니다.

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

### (1) 정적 검증 (Static Verification)

코드를 **실행하지 않고** 검사합니다.

대표 항목: 문법 검사, 타입 검사, 정적 분석, 의존성 검사, 보안 취약점 스캔

특징: 빠름 / 빌드 단계에서 차단 가능 / 런타임 오류 일부 예방 가능

### (2) 동적 검증 (Dynamic Validation)

**실제로 실행하면서** 확인합니다.

대표 항목: 단위 테스트, 통합 테스트, 시스템 테스트, 성능 테스트, 장애 복구 테스트

특징: 실제 런타임 흐름 검증 / 동시성 문제 발견 / 네트워크·스토리지 문제 검증 가능

### (3) 상태 검증 (State Validation)

현대 분산 시스템에서 매우 중요합니다.

검증 대상: 트랜잭션 상태, 세션 상태, 캐시 일관성, 메시지 큐 상태, 복제 상태, 리더 선출 상태

> "코드가 실행되었다"가 아니라  
> **"시스템 상태가 정상 규칙을 유지하는가"** 를 검증합니다.

### (4) 회귀 검증 (Regression Validation)

변경 후 기존 기능이 깨졌는지 확인합니다. CI/CD 핵심 메커니즘입니다.

```
변경
→ 자동 테스트
→ 결과 비교
→ 배포 승인
```

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 영역 | 관측 |
|---|---|
| `systemd` | 서비스 상태 |
| `dmesg` | 커널 오류 |
| `strace` | 시스템 콜 추적 |
| `perf` | 성능 분석 |
| `iostat` / `vmstat` | 자원 병목 확인 |

### Runtime

| 영역 | 관측 |
|---|---|
| Heap 상태 | 메모리 누수 |
| Thread 상태 | 교착 / 경쟁 상태 |
| GC 로그 | 메모리 압박 |
| Event Loop 상태 | 블로킹 여부 |
| Open File 수 | FD 누수 |

### Kubernetes

| 영역 | 관측 |
|---|---|
| Readiness Probe | 서비스 정상 여부 |
| Liveness Probe | 프로세스 생존 여부 |
| Events | 스케줄링 / 재시작 |
| Metrics | CPU / Memory / Network |
| Logs | 런타임 오류 |
| Rollout 상태 | 배포 검증 |

특히 Kubernetes에서는 다음을 **분리하여** 검증합니다.

- "프로세스가 살아있는가?"
- "실제 요청 처리가 가능한가?"
- "트래픽 수용 가능한 상태인가?"
