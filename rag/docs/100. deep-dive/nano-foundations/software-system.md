# 소프트웨어 시스템 (Software System)

> 정독: 0회

## 1. 이 기술이 무엇인가

소프트웨어 시스템은:

> 특정 목적을 수행하기 위해 프로그램, 데이터, 실행 구조, 통신 규칙, 자원 관리 메커니즘이 결합되어 동작하는 **실행 가능한 컴퓨팅 체계**

### 핵심 관점

단순 코드 집합이 아니라 다음 전체를 포함하는 **전체 동작 시스템**입니다.

- 실행 상태 (Runtime State)
- 프로세스 및 스레드 구조
- 메모리 사용 구조
- 네트워크 및 저장소 흐름
- 운영 및 장애 처리 체계

> "코드"보다 더 큰 개념이며,  
> 실제로 **CPU · 메모리 · 네트워크 · 스토리지 위에서 동작하는 전체 실행 구조**를 의미합니다.

---

## 2. 시스템 어디에서 등장하는가

소프트웨어 시스템은 컴퓨터 환경 전반에서 등장합니다.

| 영역 | 예시 |
|---|---|
| **운영체제** | Linux Kernel |
| **데이터베이스** | PostgreSQL, MySQL |
| **웹 서비스** | API 서버 |
| **분산 시스템** | Kafka, Redis Cluster |
| **클라우드 플랫폼** | Kubernetes |
| **금융 시스템** | 결제 / 정산 시스템 |
| **런타임 환경** | JVM, CLR |
| **AI 시스템** | 추론 서버 |

### 현대 시스템 구성

프로세스, 스레드, 네트워크 연결, 메시지 큐, 저장소, 캐시, 관측 시스템, 배포 시스템의 조합으로 구성됩니다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

소프트웨어 시스템은 **모든 시스템 자원을 동시에 사용**합니다.

| 자원 | 영향 항목 |
|---|---|
| **CPU** | 연산, 스케줄링 |
| **Memory** | 객체, 캐시, 상태 유지 |
| **Network** | 서비스 간 통신 |
| **Disk** | 데이터 저장 및 로그 |

시스템 구조에 따라 병목 자원이 달라집니다.

| 시스템 유형 | 주요 병목 |
|---|---|
| 계산 중심 시스템 | CPU |
| 캐시 시스템 | Memory |
| API Gateway | Network |
| 데이터베이스 | Disk I/O |

---

## 4. 왜 중요한가

소프트웨어 시스템은 **실제 서비스 품질을 결정**합니다.

핵심 요소: 안정성, 확장성, 복구 가능성, 데이터 무결성, 성능, 운영 가능성

### 잘못 설계된 시스템의 결과

장애 전파, 자원 고갈, 데이터 불일치, 스케일 실패, 운영 복잡도 증가

> 특히 현대 대규모 시스템에서는  
> "코드 자체"보다 **"시스템 구조와 실행 흐름"이 더 중요해지는 경우가 많습니다.**

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 장애 대부분은 **시스템 수준 문제**에서 발생합니다.

| 장애 | 원인 |
|---|---|
| **CPU 100%** | 스레드 폭증 |
| **OOM** | 메모리 누수 |
| **Latency 증가** | 네트워크 병목 |
| **DB 과부하** | 잘못된 데이터 흐름 |
| **장애 전파** | 강한 결합 구조 |
| **Pod 재시작 반복** | 런타임 상태 불안정 |
| **파일 디스크립터 고갈** | 자원 회수 실패 |

특히 분산 시스템에서는 네트워크 지연, 부분 실패(Partial Failure), 상태 불일치가 핵심 장애 원인이 됩니다.

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

### (1) 실행 구조 (Runtime Structure)

소프트웨어 시스템은 실행되면 다음 구조로 변환됩니다.

프로세스, 스레드, 힙 메모리, 스택 메모리, 파일 디스크립터, 네트워크 소켓

```
정적 코드 → 동적 실행 상태
```

### (2) 데이터 흐름 (Data Flow)

시스템 내부에서는 데이터가 지속적으로 이동합니다.

대표 흐름: 메모리 ↔ CPU, 프로세스 ↔ 프로세스, 서비스 ↔ 서비스, 애플리케이션 ↔ DB, 사용자 ↔ 서버

좋은 시스템은 불필요한 복사 감소, 병목 최소화, 흐름 제어(backpressure), 상태 일관성 유지를 수행합니다.

### (3) 자원 관리 (Resource Management)

운영체제가 자원을 제공하지만, 실제 사용 전략은 시스템이 결정합니다.

관리 대상: CPU 시간, 메모리 점유, 네트워크 연결, 디스크 I/O, 스레드 수, 파일 핸들

자원 관리 실패는 성능 저하 → 장애 → 시스템 정지로 이어집니다.

### (4) 상태 관리 (State Management)

상태 종류: 세션 상태, 트랜잭션 상태, 캐시 상태, 분산 노드 상태, 런타임 상태

> 특히 분산 환경에서는  
> **상태 일관성 유지가 가장 어려운 문제 중 하나**입니다.

### (5) 의존성 구조 (Dependency Structure)

잘못된 의존성 구조는 장애 전파, 배포 어려움, 테스트 불가능성, 확장 제한을 유발합니다.

현대 시스템은 보통 **느슨한 결합(Loose Coupling), 명확한 경계, 장애 격리**를 목표로 설계합니다.

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 영역 | 관측 |
|---|---|
| `ps` / `top` / `htop` | 프로세스 상태 |
| `vmstat` | 메모리 및 스케줄링 |
| `iostat` | 디스크 I/O |
| `ss` / `netstat` | 네트워크 연결 |
| `lsof` | 파일 및 소켓 |
| `perf` | CPU 병목 |

### Runtime

| 영역 | 관측 |
|---|---|
| Heap Dump | 객체 상태 |
| Thread Dump | 실행 흐름 |
| GC Log | 메모리 압박 |
| Event Queue | 비동기 처리 상태 |
| Lock 상태 | 동기화 문제 |

### Kubernetes

| 영역 | 관측 |
|---|---|
| Pod | 실행 단위 |
| Deployment | 시스템 배포 상태 |
| Service | 네트워크 구조 |
| HPA | 스케일링 상태 |
| Resource Limit | 자원 사용 제한 |
| Events | 장애 및 재시작 |
| Metrics | CPU / Memory / Network |

> 특히 Kubernetes는 소프트웨어 시스템을  
> **배포 · 격리 · 복구 · 확장** 가능한 운영 단위로 관리합니다.
