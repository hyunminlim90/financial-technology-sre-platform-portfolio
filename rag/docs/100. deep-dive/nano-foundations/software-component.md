# 소프트웨어 구성 요소 (Software Component)

> 정독: 0회

## 1. 이 기술이 무엇인가

소프트웨어 구성 요소는:

> 시스템 내부에서 특정 책임과 기능을 수행하도록 분리된 **독립 실행 단위 또는 논리 모듈**

### 핵심 특징

- 명확한 책임
- 캡슐화
- 인터페이스 기반 통신
- 독립적 변경 가능성
- 재사용 가능성

### 핵심 관점

단순 코드 파일이 아니라 다음을 포함하는 **시스템 구조 단위**입니다.

- 상태 (State)
- 실행 로직
- 데이터 흐름
- 의존성
- 자원 사용 방식

### 대표 형태

모듈(Module), 라이브러리(Library), 서비스(Service), 프로세스(Process), 플러그인(Plugin), 패키지(Package)

---

## 2. 시스템 어디에서 등장하는가

소프트웨어 구성 요소는 거의 모든 시스템 구조에서 등장합니다.

| 계층 | 구성 요소 예시 |
|---|---|
| **운영체제** | 스케줄러, 파일 시스템 |
| **애플리케이션** | 인증 모듈, 결제 모듈 |
| **데이터베이스** | 스토리지 엔진 |
| **네트워크** | 프록시, 로드밸런서 |
| **Kubernetes** | Pod, Controller |
| **분산 시스템** | 메시지 브로커, 캐시 노드 |

현대 시스템은 "하나의 거대한 프로그램"보다 **"여러 구성 요소들의 협력 구조"** 로 동작합니다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

구성 요소 설계 방식은 **시스템 자원 사용 패턴을 결정**합니다.

| 자원 | 영향 항목 |
|---|---|
| **CPU** | 실행 흐름, 스레드 모델 |
| **Memory** | 객체 생명주기, 캐시 |
| **Network** | 서비스 간 통신 |
| **Disk** | 상태 저장 및 로그 |

| 구성 방식 | 영향 |
|---|---|
| 과도한 서비스 분리 | 네트워크 비용 증가 |
| 상태 공유 과다 | 메모리 충돌 증가 |
| 거대한 단일 컴포넌트 | CPU 병목 집중 |
| 잘못된 캐시 컴포넌트 | 메모리 폭증 |

---

## 4. 왜 중요한가

구성 요소 설계는 시스템의 유지보수성, 확장성, 장애 격리, 배포 안정성, 테스트 가능성을 결정합니다.

### 좋은 구성 요소 구조의 특징

책임 분리, 낮은 결합도, 높은 응집도, 명확한 인터페이스, 독립적 장애 격리

### 잘못 설계 시 결과

장애 전파, 순환 의존성, 배포 충돌, 테스트 불가능성, 성능 병목

---

## 5. 실제 장애와 어떤 관련이 있는가

실제 운영 장애 상당수는 **구성 요소 경계 설계 실패**에서 발생합니다.

| 장애 | 원인 |
|---|---|
| **Cascading Failure** | 강한 컴포넌트 결합 |
| **Memory Leak** | 상태 관리 책임 불명확 |
| **Deadlock** | 컴포넌트 간 락 충돌 |
| **배포 실패** | 의존성 얽힘 |
| **API Timeout** | 과도한 동기 호출 |
| **장애 분석 어려움** | 책임 경계 불명확 |

> 특히 분산 시스템에서는  
> **구성 요소 간 호출 구조가 곧 장애 전파 경로**가 됩니다.

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

### (1) 캡슐화 (Encapsulation)

구성 요소는 내부 구현을 숨깁니다. 외부에는 API, 함수, 인터페이스, 메시지 규약만 노출합니다.

핵심 목적: 내부 변경 영향 차단 / 독립적 진화 가능성 확보

### (2) 인터페이스 기반 통신

구성 요소는 직접 내부 상태를 공유하지 않고 인터페이스를 통해 상호작용합니다.

| 방식 | 특징 |
|---|---|
| **함수 호출** | 프로세스 내부 |
| **IPC** | 프로세스 간 |
| **HTTP / gRPC** | 서비스 간 |
| **메시지 큐** | 비동기 통신 |

인터페이스 안정성이 시스템 안정성에 직접 연결됩니다.

### (3) 상태 관리 (State Ownership)

구성 요소는 자신이 관리하는 상태 범위를 명확히 가져야 합니다.

관리 대상: 세션 상태, 캐시 상태, 연결 상태, 트랜잭션 상태

상태 소유권이 불명확하면 Race Condition, 데이터 충돌, 중복 처리, 메모리 누수가 발생합니다.

### (4) 의존성 방향 (Dependency Direction)

핵심 원칙:

- 하위 구성 요소는 상위를 몰라야 함
- 순환 의존성 제거
- 인터페이스 중심 연결

의존성 구조는 빌드 안정성, 배포 안정성, 테스트 가능성에 직접 영향을 줍니다.

### (5) 런타임 실체 (Runtime Entity)

구성 요소는 실행 시 실제 런타임 자원으로 변환됩니다.

| 논리 구조 | 런타임 실체 |
|---|---|
| 서비스 | 프로세스 |
| 객체 | Heap 메모리 |
| 큐 | 메모리 버퍼 |
| API | 네트워크 소켓 |
| 캐시 | 메모리 영역 |

> 구성 요소 설계는 결국  
> **CPU 사용 패턴 · 메모리 구조 · 네트워크 흐름**으로 이어집니다.

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 영역 | 관측 |
|---|---|
| `ps` / `top` | 프로세스 단위 |
| `lsof` | 파일 / 소켓 사용 |
| `ss` / `netstat` | 컴포넌트 통신 |
| `perf` | CPU 병목 |
| `vmstat` | 메모리 압박 |

### Runtime

| 영역 | 관측 |
|---|---|
| Heap Dump | 객체 구조 |
| Thread Dump | 실행 흐름 |
| Connection Pool | 자원 상태 |
| Queue 상태 | 비동기 흐름 |
| Lock 상태 | 동기화 문제 |

### Kubernetes

| 영역 | 관측 |
|---|---|
| Pod | 실행 구성 요소 |
| Service | 컴포넌트 연결 |
| Deployment | 배포 단위 |
| ConfigMap / Secret | 구성 데이터 |
| HPA | 확장 상태 |
| NetworkPolicy | 통신 경계 |

> 특히 Kubernetes에서는  
> **구성 요소 경계가 곧 운영 경계**가 됩니다.
