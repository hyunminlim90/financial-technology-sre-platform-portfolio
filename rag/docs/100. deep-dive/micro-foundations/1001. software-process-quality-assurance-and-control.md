# 소프트웨어 프로세스 품질 보증 및 제어 (Software Process Quality Assurance and Control)

> 정독: 1회

## 1. 무엇인가

소프트웨어 프로세스 품질 보증 및 제어(Software Process Quality Assurance and Control)는 소프트웨어 개발 과정이 정의된 절차와 기준에 따라 수행되고 있는지 확인하고, 산출물의 품질을 지속적으로 검증하는 활동이다.

일반적으로 두 영역으로 구분된다.

| 구분 | 중심 | 관리 대상 |
|------|------|-----------|
| **Quality Assurance (QA)** | 프로세스 중심 | 개발 절차, 설계 기준, 테스트 기준, 배포 절차, 운영 절차의 적합성 |
| **Quality Control (QC)** | 산출물 중심 | 소스코드, 문서, 테스트 결과, 배포 결과의 품질 |

---

## 2. 시스템 어디에서 등장하는가

품질 보증과 품질 제어는 소프트웨어 개발 생명주기(SDLC) 전체에 적용된다.

```
Requirements
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
```

**대표 적용 영역:**
- 요구사항 검토
- 설계 검토
- 코드 리뷰
- 테스트 검증
- 배포 승인
- 운영 변경 관리

> 특정 기술 계층이 아니라 개발과 운영 **프로세스 전체**에 존재한다.

---

## 3. 어떤 자원에 가장 영향이 큰가

직접적으로 특정 시스템 자원을 소비하는 기술은 아니다.

**주요 영향 대상:**
- 개발 비용
- 운영 비용
- 장애 복구 비용
- 변경 관리 비용
- 품질 관리 비용

간접적으로는 CPU · Memory · Network · Disk 관련 장애를 감소시키는 효과가 있다.

**예시:**

| 검증 부재 | 운영 결과 |
|-----------|-----------|
| 성능 테스트 부재 | CPU Saturation 운영 유입 |
| 메모리 검증 부재 | Memory Leak 운영 유입 |
| 네트워크 테스트 부재 | Timeout 장애 운영 유입 |

---

## 4. 왜 중요한가

품질 문제는 대부분 운영 환경에서 발견될 경우 비용이 급격히 증가한다.

**품질 관리의 목적:**
- 결함 조기 발견
- 운영 장애 예방
- 변경 안정성 확보
- 재현 가능성 확보
- 배포 안정성 확보

특히 대규모 서비스에서는 **변경 빈도 증가 · 시스템 복잡도 증가 · 서비스 의존성 증가**로 인해 품질 관리 체계가 필수적이다.

---

## 5. 실제 장애와 어떤 관련이 있는가

대부분의 운영 장애는 기술 자체보다 **품질 관리 실패**와 연결된다.

**대표 사례:**

| 원인 | 결과 |
|------|------|
| 테스트 부족 | 배포 이후 기능 오류 발생 |
| 코드 리뷰 부재 | 동시성 오류 운영 유입 |
| 성능 검증 부족 | CPU Saturation, Thread Pool Exhaustion, Latency 증가 |
| 메모리 검증 부족 | Heap Leak, Direct Memory Leak, Metaspace Leak |
| 운영 검증 부족 | 배포 실패, 롤백 실패, 설정 오류 |

---

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘

E2E SRE 문서를 읽는 관점에서는 다음 네 가지를 이해하면 충분하다.

| 단계 | 핵심 질문 |
|------|-----------|
| 표준 정의 | 어떤 방식으로 개발할 것인가 |
| 검증 | 만든 결과가 기준을 만족하는가 |
| 승인 | 운영 환경에 반영 가능한가 |
| 측정 | 품질 상태를 수치로 확인 가능한가 |

결국 **정의 → 검증 → 승인 → 측정**의 반복 과정으로 이해할 수 있다.

---

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

품질 보증 및 제어 자체는 Linux, Runtime, Kubernetes 내부 기능이 아니다.  
그러나 **품질 활동의 결과**는 관측할 수 있다.

### Linux

| 구분 | 내용 |
|------|------|
| 관측 대상 | 프로세스 상태, CPU 사용량, Memory 사용량, Network 상태, Disk 상태 |
| 대표 도구 | `top`, `vmstat`, `iostat`, `ss` |

### Runtime

| 구분 | 내용 |
|------|------|
| 관측 대상 | 예외 발생, GC 동작, Thread 상태, Connection Pool 상태 |
| 대표 자료 | Metrics, Logs, Traces, JFR, Thread Dump |

### Kubernetes

| 구분 | 내용 |
|------|------|
| 관측 대상 | 배포 성공률, 재시작 횟수, CrashLoopBackOff, Resource Usage, Error Rate |
| 대표 지표 | Deployment Success Rate, Pod Restart Count, SLO, SLI, Error Budget |

## E2E SRE 문서 관점 핵심 정리

> 소프트웨어 프로세스 품질 보증 및 제어는 개발 절차가 올바르게 수행되는지 확인하고, 산출물의 품질을 검증하는 활동이다.

- **QA**는 프로세스를 관리하고
- **QC**는 결과물을 검증한다.

E2E SRE 관점에서 품질 관리는 단순 테스트가 아니라 **운영 환경에 장애가 유입되지 않도록 하는 사전 통제 체계**로 이해하는 것이 중요하다.

```
품질 관리
      ↓
안정적인 배포
      ↓
안정적인 운영
      ↓
높은 서비스 신뢰성
```
