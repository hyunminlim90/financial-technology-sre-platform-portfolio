# Software Life Cycle (소프트웨어 생명주기)

> 정독: 1회

## 1. 무엇인가

소프트웨어 생명주기(Software Life Cycle)는 소프트웨어가 기획되고 개발되어 운영된 후 최종적으로 폐기될 때까지의 전체 과정을 의미한다.

실무에서는 이를 체계적으로 관리하기 위해 소프트웨어 개발 생명주기(SDLC, Software Development Life Cycle) 형태로 운영한다.

일반적으로 다음 단계로 구성된다.

```
Requirements
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
      ↓
Maintenance
      ↓
Retirement
```

> 생명주기의 목적은 소프트웨어를 예측 가능하고 관리 가능한 방식으로 개발 및 운영하는 것이다.

---

## 2. 시스템 어디에서 등장하는가

소프트웨어 생명주기는 특정 기술 계층이 아니라 시스템 전체에 적용된다.

**대표 적용 영역:**
- 비즈니스 요구사항
- 아키텍처 설계
- 애플리케이션 개발
- 테스트 환경
- 배포 환경
- 운영 환경
- 유지보수 환경

> 기획 → 개발 → 운영 → 폐기까지 전 과정을 포함한다.

---

## 3. 어떤 자원에 가장 영향이 큰가

생명주기는 특정 시스템 자원을 직접 소비하는 기술이 아니다.

**주요 영향 대상:**
- 개발 시간
- 개발 비용
- 운영 비용
- 유지보수 비용
- 장애 대응 비용

간접적으로는 CPU · Memory · Network · Disk 관련 자원 사용 방식에 영향을 준다.

**예시:**

| 원인 | 결과 |
|------|------|
| 설계 품질 저하 | CPU 사용량 증가 |
| 테스트 부족 | Memory Leak 운영 유입 |
| 배포 절차 부재 | 운영 장애 발생 |

---

## 4. 왜 중요한가

소프트웨어는 개발 완료 시점에 끝나는 것이 아니라 **운영과 유지보수 기간이 훨씬 길다.**

**생명주기 관리의 목적:**
- 예측 가능한 개발
- 안정적인 배포
- 지속적인 운영
- 변경 관리
- 장애 대응
- 기술 부채 관리

생명주기 관리가 없으면 요구사항 누락, 설계 오류, 배포 실패, 운영 장애, 유지보수 어려움 등이 발생할 수 있다.

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 장애는 특정 단계의 실패가 이후 단계로 전파되면서 발생하는 경우가 많다.

| 단계 | 원인 | 결과 |
|------|------|------|
| 요구사항 | 비즈니스 요구사항 누락 | 기능 오류 |
| 설계 | 확장성 고려 부족 | CPU Saturation |
| 설계 | 메모리 설계 오류 | Memory Leak |
| 구현 | 동시성 처리 오류 | Deadlock, Lock Contention, Race Condition |
| 테스트 | 성능 검증 누락 | 운영 환경 Latency 증가 |
| 테스트 | 부하 검증 누락 | Thread Pool Exhaustion |
| 배포 | 설정 오류 / 배포 실패 | Rollback 실패 |
| 운영 | 모니터링 부재 | 장애 탐지 실패, 복구 지연 |

---

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘

E2E SRE 문서를 읽는 관점에서는 다음 흐름만 이해하면 충분하다.

| 단계 | 핵심 내용 |
|------|-----------|
| 요구사항 정의 | 무엇을 만들어야 하는가 |
| 설계 | 어떻게 구현할 것인가 |
| 구현 | 실제 기능 개발 |
| 검증 | 요구사항 충족 여부 확인 |
| 배포 | 운영 환경 반영 |
| 운영 | 모니터링, 장애 대응, 성능 관리 |
| 개선 | 변경, 최적화, 기능 확장 |

결국 다음의 반복 구조로 이해할 수 있다.

```
요구사항
      ↓
설계
      ↓
구현
      ↓
검증
      ↓
배포
      ↓
운영
      ↓
개선
```

---

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

소프트웨어 생명주기 자체는 Linux나 Runtime 내부 기능이 아니다. **생명주기의 결과물**이 운영 환경에서 관측된다.

### Linux

| 구분 | 내용 |
|------|------|
| 관측 대상 | 프로세스, CPU, Memory, Network, Disk |
| 대표 도구 | `top`, `vmstat`, `iostat`, `ss`, `sar` |

### Runtime

| 구분 | 내용 |
|------|------|
| 관측 대상 | GC, Thread, Heap, Lock, Connection Pool, Exception |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 구분 | 내용 |
|------|------|
| 관측 대상 | Deployment, Pod, Container, Resource Usage, Restart Count |
| 대표 명령 | `kubectl get`, `kubectl describe`, `kubectl logs`, `kubectl top` |

## E2E SRE 문서 관점 핵심 정리

> 소프트웨어 생명주기는 요구사항 → 설계 → 구현 → 테스트 → 배포 → 운영 → 유지보수 → 폐기까지의 전체 과정을 의미한다.

중요한 것은 특정 개발 단계가 아니라 **변경이 운영 환경까지 전달되는 전체 흐름을 관리하는 것**이다.

E2E SRE 관점에서는 다음과 같은 지속적인 순환 구조로 이해하면 된다.

```
개발
      ↓
테스트
      ↓
배포
      ↓
운영
      ↓
관측
      ↓
개선
```

> 대부분의 운영 장애는 운영 단계 자체가 아니라 요구사항, 설계, 구현, 테스트 단계에서 발생한 문제가 운영 환경으로 전파된 결과로 나타난다.
