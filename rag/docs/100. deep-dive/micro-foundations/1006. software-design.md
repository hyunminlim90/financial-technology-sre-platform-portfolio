# Software Design (소프트웨어 설계)

> 정독: 1회

## 1. 무엇인가

소프트웨어 설계(Software Design)는 요구사항을 실제 구현 가능한 기술 구조로 변환하는 과정이다.

요구사항이 시스템이 수행해야 할 기능과 품질 목표를 정의한다면, 설계는 이를 구현하기 위한 구조와 구성 방식을 정의한다.

설계의 목적은 다음과 같다.

- 요구사항을 구현 가능한 형태로 변환
- 시스템 구조 정의
- 컴포넌트 역할 정의
- 데이터 흐름 정의
- 인터페이스 정의
- 품질 속성 반영

설계는 구현 이전 단계에서 시스템의 구조적 방향을 결정하는 활동이다.

---

## 2. 시스템 어디에서 등장하는가

설계는 요구사항과 구현 사이에 위치한다.

```
Requirements
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Operation
```

설계는 시스템 전반에 적용된다.

**대표 설계 대상**

- 시스템 구조
- 모듈 구조
- 서비스 구조
- 데이터 구조
- 통신 구조
- 배포 구조
- 운영 구조

설계 결과는 이후 소스코드, 테스트, 배포, 운영의 기준이 된다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

설계는 네 가지 주요 시스템 자원 모두에 직접적인 영향을 준다.

| 자원 | 설계 영향 |
|------|-----------|
| CPU | 처리 구조, 병렬성, 연산 방식 |
| Memory | 데이터 구조, 캐시 구조 |
| Network | 통신 방식, 호출 구조 |
| Disk | 저장 구조, 데이터 접근 방식 |

**예시**

- **CPU**: 동기 처리, 비동기 처리, 병렬 처리
- **Memory**: 캐시 사용, 객체 유지 전략, 데이터 저장 구조
- **Network**: 서비스 간 호출, 메시지 전달, 데이터 전송량
- **Disk**: 저장 방식, 조회 방식, 데이터 보관 정책

설계는 자원 사용 패턴을 결정하는 핵심 요소이다.

---

## 4. 왜 중요한가

설계 단계에서 결정된 구조는 구현 이후 변경 비용이 매우 크다.

설계는 다음 특성에 직접 영향을 준다.

- 성능
- 확장성
- 가용성
- 안정성
- 유지보수성
- 운영 복잡도

좋은 설계는 변경 용이성, 장애 격리, 확장 가능성, 운영 단순화를 제공한다.

반대로 설계 결함은 운영 단계에서 지속적으로 문제를 발생시킬 수 있다.

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 환경의 많은 장애는 구현보다 설계 단계에서 시작된다.

**CPU 관련**
- 설계 문제: 병렬 처리 고려 부족, 병목 구간 집중
- 결과: CPU Saturation, Latency 증가, TPS 감소

**Memory 관련**
- 설계 문제: 과도한 상태 유지, 비효율적 캐시 설계
- 결과: Memory Leak, OOM, GC 증가

**Network 관련**
- 설계 문제: 과도한 동기 호출, 서비스 간 강한 의존성
- 결과: Timeout, Retry 증가, Cascading Failure

**Disk 관련**
- 설계 문제: 비효율적 데이터 접근, 과도한 저장 작업
- 결과: Disk Saturation, Storage Bottleneck, Database Latency 증가

**가용성 관련**
- 설계 문제: 단일 장애 지점 존재
- 결과: 서비스 전체 중단, 복구 지연

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

E2E SRE 문서를 읽는 관점에서는 설계를 다음 다섯 가지 관점으로 이해하면 충분하다.

| 관점 | 핵심 질문 |
|------|-----------|
| **구조 분리** | 무엇을 하나의 단위로 나눌 것인가 |
| **책임 분리** | 각 구성 요소가 무엇을 담당하는가 |
| **데이터 흐름** | 데이터가 어디서 생성되고 어디로 전달되는가 |
| **의존성 관리** | 어떤 구성 요소가 어떤 구성 요소에 의존하는가 |
| **장애 격리** | 하나의 장애가 어디까지 영향을 줄 수 있는가 |

**설계의 핵심 흐름**

```
요구사항
    ↓
구조 정의
    ↓
책임 정의
    ↓
인터페이스 정의
    ↓
구현
```

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

설계 자체는 직접 관측되지 않는다. **설계 결과**가 운영 환경에서 관측된다.

### Linux

| 항목 | 내용 |
|------|------|
| 관측 대상 | CPU 사용률, Memory 사용률, Network 사용량, Disk 사용량, 프로세스 구조 |
| 대표 도구 | `top`, `vmstat`, `iostat`, `sar`, `ss` |

### Runtime

| 항목 | 내용 |
|------|------|
| 관측 대상 | Thread 구조, Connection 구조, Heap 사용, GC 동작, 예외 발생 패턴 |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 항목 | 내용 |
|------|------|
| 관측 대상 | Pod 구조, 서비스 구조, 트래픽 분산, Replica 구성, 장애 복구 동작 |
| 대표 명령 | `kubectl get`, `kubectl describe`, `kubectl logs`, `kubectl top` |

## E2E SRE 문서 관점 핵심 정리

소프트웨어 설계는 **요구사항을 실제 구현 가능한 기술 구조로 변환하는 과정**이다.

설계의 핵심은 다음을 정의하는 것이다.

- 구조를 어떻게 나눌 것인가
- 책임을 어떻게 분리할 것인가
- 데이터를 어떻게 흐르게 할 것인가
- 장애를 어떻게 격리할 것인가

E2E SRE 관점에서는 다음 흐름으로 연결된다.

```
설계
  ↓
구현
  ↓
자원 사용 패턴
  ↓
운영 특성
  ↓
장애 특성
```

> 많은 운영 장애는 구현 실수보다 병목 구조, 과도한 의존성, 확장성 부족, 장애 격리 실패와 같은 설계 단계의 결정에서 시작된다.
