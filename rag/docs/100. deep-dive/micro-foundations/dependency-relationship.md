# 의존성 관계(Dependency Relationship)

> 정독: 0회

## 1. 이 기술이 무엇인가

의존성 관계는:

> 하나의 소프트웨어 구성 요소가 다른 구성 요소의 기능이나 데이터에 의존하는 **구조적 관계**

즉:

- 어떤 모듈이 다른 모듈의 기능을 호출하거나
- 데이터 구조를 사용하거나
- 실행 결과를 필요로 하는 상태

를 의미합니다.

> **핵심:** "변경과 실행 흐름이 어떤 방향으로 연결되는가"

---

## 2. 시스템 어디에서 등장하는가

의존성 관계는 모든 소프트웨어 시스템에 존재합니다.

| 영역 | 의존성 예시 |
|------|-----------|
| 애플리케이션 | 서비스 → 저장소 |
| 운영체제 | 커널 → 드라이버 |
| 데이터베이스 | Query Engine → Storage Engine |
| 네트워크 | API → 인증 시스템 |
| Kubernetes | Pod → API Server |
| 빌드 시스템 | 패키지 → 외부 라이브러리 |

실행 시스템은 결국 **의존성 그래프(Dependency Graph)** 위에서 동작합니다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

의존성 관계는 주로 CPU 실행 흐름, 메모리 참조 구조, 네트워크 호출 체인에 영향이 큽니다.

### CPU

의존성 호출이 많을수록 함수 호출 증가, Context 전환 증가, 실행 경로 복잡화가 발생합니다.

### Memory

강한 의존성은 객체 참조 증가, 메모리 생명주기 복잡화, GC 추적 범위 증가를 유발할 수 있습니다.

### Network

분산 시스템에서는 서비스 간 의존성이 API 호출 체인, Retry 전파, Timeout 전파로 이어집니다.

### Disk

간접적으로 트랜잭션 로그, 캐시 계층, 파일 접근 흐름에 영향을 줍니다.

---

## 4. 왜 중요한가

소프트웨어 시스템의 유지보수성과 안정성은 기능 자체보다 **"의존성이 어떻게 연결되어 있는가"** 에 크게 좌우됩니다.

| 이유 | 설명 |
|------|------|
| 변경 격리 | 수정 영향 범위 축소 |
| 테스트 용이성 | 독립 테스트 가능 |
| 장애 전파 차단 | 연쇄 장애 감소 |
| 교체 가능성 | 구현 변경 가능 |
| 확장성 | 기능 추가 용이 |

반대로, 잘못된 의존성 구조는 강한 결합, 순환 참조, 장애 전파, 변경 비용 폭증으로 이어집니다.

---

## 5. 실제 장애와 어떤 관련이 있는가

실제 대규모 장애는 의존성 전파 구조 때문에 커집니다.

| 장애 | 의존성 원인 |
|------|-----------|
| 연쇄 Timeout | 동기 호출 체인 |
| 전체 장애 전파 | 강한 서비스 결합 |
| Deadlock | 순환 의존 |
| 메모리 누수 | 참조 해제 실패 |
| 배포 실패 | 버전 의존 충돌 |
| 장애 복구 지연 | Shared Dependency 병목 |

특히 분산 시스템에서는 **"의존성 깊이"** 가 곧 장애 전파 깊이가 됩니다.

---

## 6. 핵심 메커니즘

### (1) 정적 의존성과 동적 의존성

의존성은 두 종류로 나뉩니다.

| 종류 | 의미 |
|------|------|
| 정적 의존성 | 코드/설계 수준 참조 |
| 동적 의존성 | 런타임 실제 호출 |

`import`, 라이브러리 링크, 인터페이스 참조는 **정적 의존성**입니다.

실제 함수 호출과 네트워크 호출은 **동적 의존성**입니다.

### (2) 결합도(Coupling)

| 상태 | 특징 |
|------|------|
| 강한 결합 | 변경 영향 큼 |
| 약한 결합 | 독립성 높음 |

**강한 결합의 특징:**

- 내부 구조 직접 참조
- 구현체 의존
- 변경 시 연쇄 수정

**약한 결합의 특징:**

- 인터페이스 기반
- 추상화 의존
- 독립 교체 가능

### (3) 의존성 방향(Direction)

좋은 시스템은 의존성이 일정 방향으로 흐릅니다.

**핵심 원칙:**

- 상위 정책은 하위 구현 세부사항에 직접 의존하지 않음
- 추상 계층이 안정적이어야 함

잘못되면 순환 의존(Circular Dependency), 구조 붕괴, 테스트 불가능이 발생합니다.

### (4) 런타임 호출 체인

실행 시 의존성은 실제 호출 흐름으로 나타납니다.

- 함수 호출
- 프로세스 호출
- RPC 호출
- DB 접근
- 메시지 소비

CPU는 결국 메모리 주소를 따라 `A → B → C` 형태로 실행 흐름을 이동합니다.

### (5) 장애 전파(Propagation)

분산 시스템에서 매우 중요합니다. 인증 서비스 장애, DB 지연, 메시지 큐 적체가 의존성 체인을 따라 확산됩니다.

그래서 다음과 같은 격리 전략이 필요합니다:

- Timeout
- Retry 제한
- Circuit Breaker
- Bulkhead

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 도구 | 관측 대상 |
|------|----------|
| ldd | 라이브러리 의존성 |
| strace | 시스템 호출 흐름 |
| pstree | 프로세스 의존 구조 |
| lsof | 파일/소켓 참조 관계 |

### Runtime

| 영역 | 관측 |
|------|------|
| Call Stack | 함수 호출 관계 |
| Heap Graph | 객체 참조 구조 |
| Thread Dump | 실행 흐름 |
| Trace | 서비스 호출 체인 |

### Kubernetes / 분산 시스템

| 대상 | 의미 |
|------|------|
| Service Graph | 서비스 의존 관계 |
| Distributed Trace | 요청 전파 흐름 |
| Istio/Service Mesh | 호출 체인 |
| Dependency Map | 장애 전파 구조 |

대규모 시스템에서는 **의존성 맵 자체가 운영 핵심 데이터**입니다.
