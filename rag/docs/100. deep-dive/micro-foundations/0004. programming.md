# Programming (프로그래밍)

> 정독: 1회

## 1. 무엇인가

프로그래밍(Programming)은 문제를 해결하기 위한 논리적 절차를 설계하고 이를 컴퓨터가 실행할 수 있는 형태로 구현하는 활동이다.

프로그래밍은 단순히 소스코드를 작성하는 행위만을 의미하지 않는다.

일반적으로 다음 활동을 포함한다.

- 문제 분석
- 알고리즘 설계
- 데이터 구조 설계
- 소스코드 작성
- 테스트
- 디버깅
- 빌드
- 실행

프로그래밍의 목적은 요구사항을 컴퓨터가 수행 가능한 실행 절차로 변환하는 것이다.

---

## 2. 시스템 어디에서 등장하는가

프로그래밍은 소프트웨어가 동작하는 모든 계층에서 사용된다.

**대표 영역**

- Application
- Service
- Middleware
- Database Logic
- Operating System
- Firmware
- Embedded System
- Automation System

시스템 관점에서는 다음 위치에서 나타난다.

```
Business Logic
      ↓
Source Code
      ↓
Build Artifact
      ↓
Runtime Execution
```

즉, 프로그래밍은 특정 계층의 기술이 아니라 소프트웨어 구현 전반에 적용된다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

프로그래밍은 네 가지 주요 자원 모두에 직접적인 영향을 준다.

| 자원 | 영향 |
|------|------|
| CPU | 연산 방식, 알고리즘 효율 |
| Memory | 데이터 구조, 객체 관리 |
| Network | 통신 방식, 데이터 전송 |
| Disk | 저장 구조, I/O 처리 |

**예시**

- **CPU**: 반복문 구조, 정렬 알고리즘, 암호화 연산
- **Memory**: 데이터 구조, 객체 생성, 캐시 사용
- **Network**: API 호출, 메시지 전송, 프로토콜 처리
- **Disk**: 파일 처리, 데이터 저장, 로그 기록

---

## 4. 왜 중요한가

프로그래밍은 소프트웨어의 동작 방식을 결정한다.

동일한 요구사항이라도 구현 방식에 따라 다음이 달라질 수 있다.

- 성능
- 안정성
- 확장성
- 유지보수성
- 운영 복잡도

프로그래밍 품질은 최종적으로 다음에 직접적인 영향을 준다.

- 시스템 품질
- 운영 안정성
- 장애 발생률

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 환경에서 발생하는 대부분의 장애는 프로그래밍 결과물과 연결된다.

**CPU 관련**
- 원인: 무한 루프, 비효율적 알고리즘, 과도한 연산
- 결과: CPU Saturation, Latency 증가, TPS 감소

**Memory 관련**
- 원인: 메모리 해제 실패, 객체 누수, 캐시 과다 사용
- 결과: Memory Leak, OOM, GC 증가

**Concurrency 관련**
- 원인: 동기화 오류, 공유 자원 경쟁
- 결과: Deadlock, Lock Contention, Race Condition

**Network 관련**
- 원인: Timeout 미설정, Connection 관리 실패
- 결과: Connection Exhaustion, Request Timeout, Retry Storm

**Storage 관련**
- 원인: 비효율적 조회, 과도한 쓰기
- 결과: Disk Saturation, Database Bottleneck

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

E2E SRE 문서를 읽는 관점에서는 프로그래밍을 다음 흐름으로 이해하면 충분하다.

```
Input
  ↓
Algorithm
  ↓
Resource Usage
  ↓
Output
```

**추가적으로 중요한 개념**

- **제어 흐름**: 조건문, 반복문, 함수 호출
- **데이터 처리**: 변수, 자료구조, 상태 변경
- **실행 환경**: 프로세스, 스레드, 메모리

> SRE 관점에서는 **어떤 언어를 사용하는가** 보다 **어떤 방식으로 자원을 사용하는가** 가 더 중요하다.

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

프로그래밍 자체는 관측 대상이 아니다. **프로그래밍의 실행 결과**가 관측된다.

### Linux

| 항목 | 내용 |
|------|------|
| 관측 대상 | Process, Thread, CPU, Memory, Network, Disk |
| 대표 도구 | `top`, `htop`, `vmstat`, `iostat`, `sar`, `ss` |

### Runtime

| 항목 | 내용 |
|------|------|
| 관측 대상 | Heap, Thread, Lock, GC, Exception, Connection Pool |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 항목 | 내용 |
|------|------|
| 관측 대상 | Pod, Container, Restart Count, Resource Usage, Health Check |
| 대표 명령 | `kubectl top`, `kubectl describe`, `kubectl logs` |

## E2E SRE 문서 관점 핵심 정리

프로그래밍은 **문제를 해결하기 위한 논리를 컴퓨터가 실행할 수 있도록 구현하는 활동**이다.

중요한 것은 특정 언어나 문법이 아니라 다음이다.

- 입력을 어떻게 처리하는가
- 상태를 어떻게 관리하는가
- CPU를 얼마나 사용하는가
- Memory를 얼마나 사용하는가
- Network와 Disk를 어떻게 사용하는가

E2E SRE 관점에서는 다음 흐름으로 이해하면 된다.

```
Programming
      ↓
Runtime Behavior
      ↓
Resource Consumption
      ↓
System Behavior
      ↓
Observability
```

> 대부분의 운영 장애는 프로그래밍 결과물이 Runtime에서 실행되면서 CPU, Memory, Network, Disk 사용 방식에 의해 발생한다.
