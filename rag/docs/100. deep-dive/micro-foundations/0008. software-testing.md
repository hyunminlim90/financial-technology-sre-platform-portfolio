# Software Testing (소프트웨어 테스트)

> 정독: 1회

## 1. 무엇인가

소프트웨어 테스트(Software Testing)는 개발된 소프트웨어가 요구사항, 설계, 품질 기준을 충족하는지 검증하고 결함을 발견하기 위한 활동이다.

테스트의 목적은 소프트웨어가 올바르게 동작함을 증명하는 것이 아니라, 잠재적인 결함과 위험을 발견하여 품질을 향상시키는 것이다.

일반적으로 테스트는 다음을 검증한다.

- 기능 정확성
- 데이터 정확성
- 성능
- 안정성
- 보안성
- 가용성
- 복구성

---

## 2. 시스템 어디에서 등장하는가

테스트는 구현 이후에만 수행되는 활동이 아니다. SDLC 전반에 걸쳐 수행된다.

```
Requirements
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
```

테스트는 다음 영역을 검증한다.

- 요구사항
- 설계
- 기능
- 데이터 흐름
- 인터페이스
- 성능
- 운영 환경

즉, 테스트는 시스템 전체 품질을 검증하는 활동이다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

테스트는 특정 자원 하나만 검증하지 않는다. 시스템 자원 전체가 검증 대상이다.

| 자원 | 테스트 대상 |
|------|-------------|
| CPU | 처리량, 연산 부하 |
| Memory | 메모리 사용량, 누수 |
| Network | 통신 품질, 지연시간 |
| Disk | 저장 성능, I/O 처리 |

**예시**

- **CPU**: 최대 처리량, 응답시간, 부하 상황
- **Memory**: 메모리 증가 추세, 메모리 회수 여부, 메모리 누수
- **Network**: 통신 오류, Timeout, 재시도 처리
- **Disk**: 읽기 성능, 쓰기 성능, 데이터 보존

---

## 4. 왜 중요한가

테스트 없이 운영 환경에 배포된 소프트웨어는 품질을 보장할 수 없다.

테스트의 목적은 다음과 같다.

- 결함 발견
- 요구사항 검증
- 변경 검증
- 운영 위험 감소
- 품질 향상

특히 변경이 반복되는 시스템에서는 기존 기능 유지, 새 기능 검증, 회귀 방지가 중요하다.

---

## 5. 실제 장애와 어떤 관련이 있는가

많은 운영 장애는 테스트 부족 또는 테스트 범위 누락과 연결된다.

**기능 테스트 부족**
- 문제: 비즈니스 로직 오류
- 결과: 잘못된 결과 반환, 업무 처리 실패

**성능 테스트 부족**
- 문제: 고부하 상황 검증 누락
- 결과: CPU Saturation, Latency 증가, TPS 감소

**메모리 테스트 부족**
- 문제: 장시간 실행 검증 누락
- 결과: Memory Leak, OOM, GC 증가

**장애 상황 테스트 부족**
- 문제: 예외 처리 검증 누락
- 결과: Retry Storm, Cascading Failure, 서비스 중단

**운영 환경 테스트 부족**
- 문제: 실제 환경과 다른 조건에서 검증
- 결과: 배포 후 장애 발생, 설정 오류, 성능 저하

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

E2E SRE 문서를 읽는 관점에서는 테스트를 다음 네 단계로 이해하면 충분하다.

| 단계 | 내용 | 검증 대상 |
|------|------|-----------|
| **단위 테스트 (Unit Test)** | 가장 작은 기능 단위 검증 | 함수, 모듈, 컴포넌트 |
| **통합 테스트 (Integration Test)** | 구성 요소 간 연동 검증 | 데이터 흐름, 인터페이스, 통신 |
| **시스템 테스트 (System Test)** | 전체 시스템 검증 | 기능, 성능, 보안, 가용성 |
| **인수 테스트 (Acceptance Test)** | 실제 사용 목적 충족 여부 검증 | 업무 시나리오, 사용자 요구사항 |

**핵심 흐름**

```
Unit
  ↓
Integration
  ↓
System
  ↓
Acceptance
```

**테스트의 핵심 질문**

- 정상 동작하는가
- 예외 상황에서도 동작하는가
- 부하 상황에서도 동작하는가
- 요구사항을 충족하는가

---

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

테스트 자체는 운영 환경 기능이 아니다. **테스트 결과**가 운영 환경에서 관측된다.

### Linux

| 항목 | 내용 |
|------|------|
| 관측 대상 | CPU Usage, Memory Usage, Network Usage, Disk Usage, Process 상태 |
| 대표 도구 | `top`, `vmstat`, `iostat`, `sar`, `ss` |

### Runtime

| 항목 | 내용 |
|------|------|
| 관측 대상 | Latency, Exception, Thread 상태, Heap 사용량, GC 동작 |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 항목 | 내용 |
|------|------|
| 관측 대상 | Pod 상태, Restart Count, Resource Usage, Health Check, Autoscaling 동작 |
| 대표 명령 | `kubectl get`, `kubectl describe`, `kubectl logs`, `kubectl top` |

## E2E SRE 문서 관점 핵심 정리

소프트웨어 테스트는 **구현된 소프트웨어가 요구사항과 품질 기준을 만족하는지 검증하는 활동**이다.

핵심 목적은 결함 발견, 품질 검증, 운영 위험 감소, 변경 검증이다.

E2E SRE 관점에서는 다음 흐름으로 이해하면 된다.

```
Testing
      ↓
Quality Verification
      ↓
Deployment Readiness
      ↓
Operational Stability
```

테스트는 단순히 기능 확인이 아니라 CPU, Memory, Network, Disk 사용 특성과 예외 상황, 고부하 상황, 장애 상황에서 시스템이 안정적으로 동작하는지를 검증하는 과정이다.

> 많은 운영 장애는 구현 단계의 결함 자체보다 검증되지 않은 코드가 운영 환경으로 유입되는 과정에서 발생한다.
