# Requirements Engineering (요구사항 공학)

> 정독: 1회

## 1. 무엇인가

요구사항 공학(Requirements Engineering)은 이해관계자의 요구를 수집하고 분석하여, 개발과 운영 과정에서 동일한 의미로 사용할 수 있는 요구사항으로 정의·관리·검증하는 공학적 활동이다.

요구사항 공학의 목적은 다음과 같다.

- 무엇을 개발해야 하는가
- 무엇을 개발하면 안 되는가
- 어떤 수준으로 동작해야 하는가
- 어떤 제약 조건을 만족해야 하는가

요구사항 공학은 소프트웨어 구현 이전에 시스템의 목표와 범위를 명확하게 정의하는 과정이다.

---

## 2. 시스템 어디에서 등장하는가

요구사항 공학은 SDLC의 가장 초기 단계에서 시작되지만, 전체 생명주기에 영향을 준다.

```
Requirements
      ↓
Analysis
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
```

요구사항은 다음 영역의 기준이 된다.

- 기능 설계
- 데이터 설계
- 테스트 시나리오
- 배포 기준
- 운영 기준
- 장애 대응 기준

즉, 요구사항은 시스템 전체의 설계 및 운영 방향을 결정하는 기준점이다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

요구사항 공학은 특정 시스템 자원을 직접 소비하지 않는다.

그러나 비기능 요구사항(Non-Functional Requirements)은 시스템 자원 설계에 직접적인 영향을 준다.

| 자원 | 영향 예시 |
|------|-----------|
| CPU | 처리량, 응답시간 목표 |
| Memory | 동시 사용자 수, 캐시 정책 |
| Network | 대역폭, 통신량, 지연시간 |
| Disk | 저장 용량, 처리량, 보존 기간 |

**예시**

- 응답시간 100ms 이하
- 동시 접속자 50,000명
- 초당 10,000건 처리
- 99.99% 가용성

이러한 요구사항은 이후 시스템 자원 설계 기준이 된다.

---

## 4. 왜 중요한가

요구사항이 불명확하면 이후 모든 단계에 영향을 미친다.

**대표 문제**

- 잘못된 기능 개발
- 불필요한 기능 개발
- 성능 부족
- 확장성 부족
- 운영 목표 부재

요구사항 공학의 목적은 다음과 같다.

- 개발 방향 명확화
- 범위 통제
- 품질 기준 정의
- 운영 목표 정의
- 이해관계자 간 합의

특히 운영 관점에서는 시스템이 어떤 수준으로 동작해야 하는지를 정의하는 기준이 된다.

---

## 5. 실제 장애와 어떤 관련이 있는가

많은 장애는 구현 단계보다 요구사항 단계의 누락에서 시작된다.

**기능 요구사항 누락**
- 예시: 결제 취소 기능 정의 누락
- 결과: 데이터 불일치, 업무 처리 실패

**성능 요구사항 누락**
- 예시: 최대 트래픽 정의 없음
- 결과: CPU Saturation, Thread Pool Exhaustion, Queue 증가

**가용성 요구사항 누락**
- 예시: 복구 시간 목표 정의 없음
- 결과: 장애 대응 지연, 복구 절차 부재

**예외 처리 요구사항 누락**
- 예시: 외부 시스템 장애 시 처리 규칙 없음
- 결과: Retry Storm, Cascading Failure, 서비스 중단

---

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

E2E SRE 문서를 읽는 관점에서는 요구사항을 다음 두 가지로 구분하면 충분하다.

**Functional Requirements (FR)**
시스템이 수행해야 하는 기능
- 사용자 인증
- 주문 생성
- 결제 처리
- 데이터 조회

**Non-Functional Requirements (NFR)**
시스템이 만족해야 하는 품질 기준
- 성능
- 가용성
- 보안성
- 확장성
- 복구성
- 유지보수성

**요구사항 공학의 핵심 흐름**

```
도출
  ↓
분석
  ↓
명세
  ↓
검증
  ↓
기준 확정
```

산출물의 핵심은 다음 질문에 답할 수 있어야 한다.

- 무엇을 만들 것인가
- 왜 만드는가
- 어떤 품질 수준을 만족해야 하는가

---

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

요구사항 자체는 Linux, Runtime, Kubernetes에서 직접 관측되지 않는다.

**요구사항을 구현한 결과**가 운영 환경에서 관측된다.

### Linux

| 항목 | 내용 |
|------|------|
| 관측 대상 | CPU Usage, Memory Usage, Network Throughput, Disk Usage |
| 대표 도구 | `top`, `vmstat`, `iostat`, `sar`, `ss` |

### Runtime

| 항목 | 내용 |
|------|------|
| 관측 대상 | Latency, Error Rate, Thread Usage, GC, Connection Pool |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 항목 | 내용 |
|------|------|
| 관측 대상 | Replica Count, Resource Usage, Availability, Restart Count, Autoscaling |
| 대표 명령 | `kubectl top`, `kubectl describe`, `kubectl logs` |

## E2E SRE 문서 관점 핵심 정리

요구사항 공학은 **시스템이 수행해야 할 기능과 만족해야 할 품질 기준을 정의하고 검증하는 활동**이다.

- **기능 요구사항(FR)** 은 무엇을 해야 하는가를 정의한다.
- **비기능 요구사항(NFR)** 은 어떤 수준으로 동작해야 하는가를 정의한다.

E2E SRE 관점에서는 다음 흐름의 출발점으로 이해하면 된다.

```
요구사항
    ↓
설계
    ↓
구현
    ↓
운영
```

특히 성능, 가용성, 확장성, 복구성 등의 비기능 요구사항은 CPU, Memory, Network, Disk 설계 기준과 운영 목표를 결정하는 핵심 입력값이다.

> 많은 운영 장애는 구현 오류보다 초기 요구사항 정의와 검증의 누락에서 시작된다.
