# Software Engineering Methodology (소프트웨어 공학 방법론)

> 정독: 1회

## 1. 무엇인가

소프트웨어 공학 방법론(Software Engineering Methodology)은 소프트웨어 개발 생명주기(SDLC)를 수행하기 위한 표준화된 절차, 규칙, 역할, 산출물, 관리 체계를 정의한 프레임워크이다.

방법론의 목적은 다음과 같다.

- 개발 절차 표준화
- 품질 일관성 확보
- 일정 예측 가능성 확보
- 변경 관리 체계화
- 운영 안정성 확보

> 방법론은 특정 기술이나 제품이 아니라 소프트웨어를 개발하고 운영하는 **방식에 대한 규칙**이다.

---

## 2. 시스템 어디에서 등장하는가

방법론은 특정 시스템 계층에 존재하지 않는다. **소프트웨어 생명주기 전체**에 적용된다.

```
Requirements
      ↓
Analysis
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
      ↓
Maintenance
```

### 대표 적용 영역

- 요구사항 관리
- 설계 검토
- 개발 절차
- 코드 리뷰
- 테스트 절차
- 배포 승인
- 변경 관리
- 운영 관리

> 즉, 방법론은 시스템 자체가 아니라 **시스템을 만드는 과정**에 적용된다.

---

## 3. 어떤 자원에 가장 영향이 큰가

방법론은 CPU, Memory, Network, Disk를 직접 사용하는 기술이 아니다.

**가장 큰 영향을 받는 자원:**

- 개발 인력
- 개발 시간
- 프로젝트 비용
- 운영 비용
- 유지보수 비용

**간접적으로** CPU / Memory / Network / Disk 관련 장애 발생 확률에 영향을 준다.

### 예시

| 절차 부재 | 결과 |
|---|---|
| 성능 검증 절차 없음 | CPU 관련 장애 증가 |
| 메모리 검증 절차 없음 | Memory Leak 운영 유입 |
| 배포 검증 절차 없음 | 운영 장애 증가 |

---

## 4. 왜 중요한가

소프트웨어 규모가 증가할수록 개인의 경험만으로 개발을 통제하기 어려워진다.

**방법론은 다음을 가능하게 한다:**

- 반복 가능한 개발
- 일관된 품질
- 변경 통제
- 위험 관리
- 장애 예방

**방법론이 부재하면:**

- 개발 방식 불일치
- 품질 편차 증가
- 일정 예측 실패
- 운영 리스크 증가

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 장애의 상당수는 기술 문제가 아니라 **방법론 적용 실패**와 연결된다.

| 원인 | 결과 |
|---|---|
| 요구사항 관리 실패 | 기능 누락 / 비즈니스 오류 / 정합성 문제 |
| 설계 검토 부족 | 확장성 부족 / 병목 구조 설계 / 단일 장애 지점 생성 |
| 코드 검증 부족 | Race Condition / Deadlock / Memory Leak |
| 테스트 부족 | 배포 후 기능 오류 / 성능 저하 / 운영 장애 |
| 변경 관리 실패 | 설정 오류 / 배포 실패 / 롤백 실패 |

> 즉, 많은 장애는 운영 단계가 아니라 **그 이전 단계에서 시작된다**.

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘

E2E SRE 문서를 읽는 관점에서는 다음 다섯 가지를 이해하면 충분하다.

| 항목 | 설명 |
|---|---|
| **Process** | 무엇을 언제 수행하는가 |
| **Role** | 누가 수행하는가 |
| **Artifact** | 무엇을 남기는가 |
| **Review** | 어떻게 검증하는가 |
| **Control** | 어떻게 승인하고 변경하는가 |

결국 방법론은 다음을 반복하는 관리 체계이다.

```
정의
  ↓
수행
  ↓
검증
  ↓
승인
  ↓
운영
  ↓
개선
```

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

방법론 자체는 Linux, Runtime, Kubernetes 내부에서 직접 관측되지 않는다. **방법론의 결과**가 관측된다.

### Linux

| 관측 대상 | 대표 도구 |
|---|---|
| 프로세스 상태 | `top` |
| CPU 사용량 | `vmstat` |
| Memory 사용량 | `iostat` |
| Network 상태 | `sar` |
| Disk 상태 | `ss` |

### Runtime

| 관측 대상 | 대표 자료 |
|---|---|
| 예외 발생 | Metrics |
| GC 상태 | Logs |
| Thread 상태 | Traces |
| Connection 상태 | Thread Dump |
| 오류율 | Heap Dump |

### Kubernetes

| 관측 대상 | 대표 명령 |
|---|---|
| 배포 성공률 | `kubectl get` |
| Pod 상태 | `kubectl describe` |
| 재시작 횟수 | `kubectl logs` |
| 에러율 | `kubectl top` |
| 자원 사용량 | |

## E2E SRE 문서 관점 핵심 정리

소프트웨어 공학 방법론은 **소프트웨어를 어떻게 개발하고 운영할 것인지에 대한 표준화된 절차와 관리 체계**이다.

중요한 것은 특정 방법론의 이름이 아니라 다음을 **정의**하는 것이다.

- 어떤 절차로 개발하는가
- 어떻게 검증하는가
- 어떻게 변경을 통제하는가
- 어떻게 품질을 유지하는가

E2E SRE 관점에서는 다음과 같이 연결된다.

```
방법론
  ↓
품질 관리
  ↓
변경 관리
  ↓
배포 안정성
  ↓
운영 안정성
```

> 많은 운영 장애는 기술 자체보다 **방법론에 의해 예방되거나 감소될 수 있다**.
