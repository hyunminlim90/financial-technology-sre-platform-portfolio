# Software Implementation (소프트웨어 구현)

> 정독: 1회

## 1. 무엇인가

소프트웨어 구현(Software Implementation)은 요구사항과 설계 결과를 실제 실행 가능한 소프트웨어로 변환하는 과정이다.

소프트웨어 공학에서는 구현(Implementation) 또는 소프트웨어 구축(Software Construction)이라고 부른다.

구현은 단순히 소스코드를 작성하는 활동만 의미하지 않는다.

일반적으로 다음 활동을 포함한다.

- 소스코드 작성
- 코드 검토
- 단위 테스트
- 디버깅
- 리팩토링
- 빌드
- 패키징

구현의 목적은 설계에서 정의된 구조와 기능을 실제 실행 가능한 형태로 만드는 것이다.

---

## 2. 시스템 어디에서 등장하는가

구현은 SDLC에서 설계와 테스트 사이에 위치한다.

```
Requirements
      ↓
Design
      ↓
Implementation
      ↓
Testing
      ↓
Deployment
      ↓
Operation
```

구현 단계에서는 다음 요소들이 실제 코드 자산으로 변환된다.

- 비즈니스 규칙
- 데이터 처리 로직
- 인터페이스
- 데이터 구조
- 예외 처리
- 상태 관리

구현 결과물은 이후 빌드 산출물, 실행 파일, 패키지, 배포 대상이 된다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

구현은 시스템의 모든 자원 사용 방식에 직접적인 영향을 준다.

| 자원 | 영향 |
|------|------|
| CPU | 연산 로직, 알고리즘 |
| Memory | 데이터 구조, 객체 생명주기 |
| Network | 통신 방식, 요청 처리 |
| Disk | 저장 및 조회 방식 |

**예시**

- **CPU**: 구현 방식에 따라 연산량, 병렬 처리, 스레드 사용이 달라진다.
- **Memory**: 구현 방식에 따라 메모리 사용량, 객체 수명, 캐시 전략이 달라진다.
- **Network**: 구현 방식에 따라 호출 횟수, 데이터 크기, 통신 패턴이 달라진다.
- **Disk**: 구현 방식에 따라 저장 빈도, 조회 빈도, I/O 처리량이 달라진다.

---

## 4. 왜 중요한가

설계가 올바르더라도 구현 품질이 낮으면 시스템 품질은 보장되지 않는다.

구현 단계는 다음 요소를 결정한다.

- 성능
- 안정성
- 확장성
- 가독성
- 유지보수성
- 운영 복잡도

특히 구현은 설계 의도를 실제 시스템 동작으로 변환하는 단계이다.

구현 품질이 낮으면 기능 오류, 성능 저하, 장애 증가, 운영 비용 증가가 발생할 수 있다.

---

## 5. 실제 장애와 어떤 관련이 있는가

운영 환경에서 발생하는 많은 장애는 구현 단계의 문제와 직접 연결된다.

**CPU 관련**
- 구현 문제: 비효율적 알고리즘, 과도한 반복 처리, 무한 루프
- 결과: CPU Saturation, Latency 증가, TPS 감소

**Memory 관련**
- 구현 문제: 객체 해제 실패, 캐시 관리 오류, 참조 유지
- 결과: Memory Leak, OOM, GC 증가

**Concurrency 관련**
- 구현 문제: 동기화 오류, 공유 자원 접근 오류
- 결과: Deadlock, Lock Contention, Race Condition

**Network 관련**
- 구현 문제: Timeout 누락, 재시도 로직 오류, 연결 관리 실패
- 결과: Connection Exhaustion, Retry Storm, Request Timeout

**Storage 관련**
- 구현 문제: 비효율적 조회, 과도한 쓰기
- 결과: Disk Saturation, Storage Bottleneck, 응답시간 증가

## 6. 현재 문맥에서 꼭 알아야 하는 핵심 메커니즘만 설명

E2E SRE 문서를 읽는 관점에서는 구현을 다음 여섯 단계로 이해하면 충분하다.

| 단계 | 내용 |
|------|------|
| **설계 해석** | 설계를 코드 구조로 변환 |
| **코드 작성** | 기능 구현 |
| **검증** | 단위 테스트, 정적 분석, 코드 검토 |
| **리팩토링** | 구조 개선, 복잡도 감소 |
| **빌드** | 실행 가능한 형태 생성 |
| **패키징** | 배포 가능한 산출물 생성 |

**핵심 흐름**

```
Design
    ↓
Coding
    ↓
Verification
    ↓
Refactoring
    ↓
Build
    ↓
Package
```

**구현 단계의 핵심 질문**

- 설계를 정확히 반영했는가
- 품질 기준을 만족하는가
- 운영 가능한 상태인가

## 7. Linux / Runtime / Kubernetes 에서 어디서 관측되는가

구현 자체는 관측 대상이 아니다. **구현 결과가 실행되면서 나타나는 동작**이 관측된다.

### Linux

| 항목 | 내용 |
|------|------|
| 관측 대상 | Process, Thread, CPU Usage, Memory Usage, Network Usage, Disk Usage |
| 대표 도구 | `top`, `vmstat`, `iostat`, `sar`, `ss` |

### Runtime

| 항목 | 내용 |
|------|------|
| 관측 대상 | Heap, Thread, GC, Exception, Connection Pool, Lock |
| 대표 자료 | Metrics, Logs, Traces, Thread Dump, Heap Dump |

### Kubernetes

| 항목 | 내용 |
|------|------|
| 관측 대상 | Container, Pod, Restart Count, Resource Usage, Health Check |
| 대표 명령 | `kubectl get`, `kubectl describe`, `kubectl logs`, `kubectl top` |

## E2E SRE 문서 관점 핵심 정리

소프트웨어 구현은 **설계 결과를 실행 가능한 소프트웨어로 변환하는 과정**이다.

핵심 활동은 코드 작성, 코드 검토, 단위 테스트, 리팩토링, 빌드, 패키징이다.

E2E SRE 관점에서는 다음 흐름으로 이해하면 된다.

```
Implementation
      ↓
Runtime Behavior
      ↓
Resource Usage
      ↓
Observability
      ↓
Operational Stability
```

> 운영 환경에서 관측되는 CPU Saturation, Memory Leak, Deadlock, Lock Contention, Connection Exhaustion, Timeout 등의 상당수는 구현 단계에서 결정된 로직과 자원 사용 방식의 결과로 나타난다.
