# 소프트웨어 런타임 아키텍처(Software Runtime Architecture)

> 정독: 0회

## 1. 이 기술이 무엇인가

소프트웨어 런타임 아키텍처는:

> 프로그램이 실제 실행 중일 때 시스템 내부에서 형성되는 **동적 실행 구조**

정적인 설계 문서나 소스코드가 아니라:

- 프로세스
- 스레드
- 메모리 구조
- 객체 배치
- 실행 흐름
- I/O 처리
- 네트워크 연결
- 동기화 상태

등이 실제로 운영체제와 하드웨어 위에서 어떻게 동작하는지를 정의합니다.

즉, **"실행 중인 시스템의 실제 구조"** 를 의미합니다.

---

## 2. 시스템 어디에서 등장하는가

런타임 아키텍처는 모든 실행 시스템에서 등장합니다.

| 영역 | 런타임 구조 |
|------|------------|
| 운영체제 | 프로세스/스레드 |
| 데이터베이스 | 트랜잭션 엔진 |
| 웹 서버 | 요청 처리 구조 |
| 메시지 시스템 | 큐 소비 구조 |
| Kubernetes | Pod 실행 구조 |
| 가상머신 | 메모리/GC 구조 |

설계 단계에서는 보이지 않지만, 실제 운영 환경에서는 런타임 구조가 시스템 동작을 결정합니다.

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

런타임 아키텍처는 모든 시스템 자원 사용 패턴에 직접 영향을 줍니다.

| 자원 | 영향 요소 |
|------|----------|
| CPU | 스레드 모델, 스케줄링 |
| Memory | 객체 생명주기, 캐시 |
| Network | 연결 구조, 동시성 |
| Disk | I/O 처리 방식 |

**예시:**

| 런타임 구조 문제 | 영향 |
|----------------|------|
| 과도한 스레드 생성 | CPU Context Switch 증가 |
| 객체 생성 폭증 | 메모리 압박 및 GC 증가 |
| 동기 I/O 남용 | 응답 지연 |
| 잘못된 큐 구조 | 병목 발생 |

---

## 4. 왜 중요한가

소프트웨어는 **"코드 자체"** 보다 **"실행 중 어떻게 움직이는가"** 가 실제 안정성과 성능을 결정합니다.

런타임 아키텍처가 중요한 이유:

- 실제 성능 결정
- 장애 전파 구조 결정
- 메모리 사용 패턴 결정
- 동시성 안정성 결정
- 확장성 결정
- 운영 가능성 결정

동일한 기능이라도 런타임 구조에 따라 처리량, 지연시간, 장애 복구력, 자원 효율이 **완전히 달라집니다**.

---

## 5. 실제 장애와 어떤 관련이 있는가

실제 운영 장애 대부분은 런타임 구조 문제에서 발생합니다.

| 장애 | 런타임 원인 |
|------|-----------|
| CPU 100% | 스레드 폭증 |
| OOM | 객체 누수 |
| 응답 지연 | Blocking I/O |
| Deadlock | 락 순환 대기 |
| 장애 전파 | 강한 동기 의존 |
| GC Stop-the-world | 메모리 압박 |
| Queue 적체 | 소비 속도 부족 |

즉, 정적 코드보다 **실행 시점의 구조와 흐름이 장애를 더 많이 결정**합니다.

---

## 6. 핵심 메커니즘

### (1) 프로세스와 스레드 구조

런타임에서는 코드가 프로세스와 스레드라는 실행 단위로 변환됩니다.

| 구조 | 역할 |
|------|------|
| 프로세스 | 독립 실행 공간 |
| 스레드 | 실제 CPU 실행 흐름 |

런타임 구조는 몇 개의 스레드를 둘지, 어떤 작업을 병렬 처리할지, 어떻게 동기화할지를 결정합니다.

### (2) 메모리 레이아웃

실행 시 프로그램은 메모리에 동적으로 배치됩니다.

| 영역 | 역할 |
|------|------|
| Heap | 동적 객체 |
| Stack | 함수 호출 |
| Code/Text | 실행 코드 |
| Shared Memory | 공유 데이터 |

메모리 구조 설계는 성능, GC 압박, 메모리 누수, 캐시 효율에 직접 영향을 줍니다.

### (3) 실행 흐름(Execution Flow)

런타임에서는 실제 작업 흐름이 생성됩니다.

- 요청 처리
- 이벤트 소비
- 큐 처리
- 트랜잭션 흐름
- 네트워크 호출

작업이 **동기/비동기/병렬/순차** 중 어떤 구조인지가 전체 시스템 지연시간을 결정합니다.

### (4) 동기화와 상태 관리

멀티스레드 환경에서는 상태 충돌 방지가 핵심입니다.

| 메커니즘 | 역할 |
|---------|------|
| Mutex | 상호 배제 |
| Semaphore | 동시 접근 제한 |
| Atomic Operation | 원자성 보장 |
| Queue | 작업 순서 제어 |

잘못 설계되면 Race Condition, Deadlock, Starvation이 발생합니다.

### (5) I/O와 커널 상호작용

런타임 시스템은 결국 운영체제 커널과 상호작용합니다.

- 파일 읽기
- 네트워크 송수신
- 디스크 쓰기
- 소켓 처리

이 과정에서 System Call, Context Switch, Interrupt, DMA 등이 발생합니다.

> 런타임 아키텍처는 단순 애플리케이션 구조가 아니라, **OS 및 하드웨어 자원 흐름과 직접 연결**됩니다.

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 도구 | 관측 대상 |
|------|----------|
| top/htop | CPU/스레드 |
| ps | 프로세스 구조 |
| vmstat | 메모리 상태 |
| iostat | I/O 구조 |
| strace | System Call |
| perf | CPU Hotspot |
| lsof | 열린 파일/소켓 |

### Runtime

| 영역 | 관측 |
|------|------|
| Heap Dump | 객체 구조 |
| Thread Dump | 실행 흐름 |
| Lock 상태 | 동기화 문제 |
| Queue 상태 | 처리 병목 |
| Connection Pool | 자원 사용량 |

### Kubernetes

| 영역 | 관측 |
|------|------|
| Pod | 실행 단위 |
| Container | 런타임 격리 |
| Resource Limit | CPU/Memory 제한 |
| HPA | 런타임 확장 |
| Probe | 생존 상태 |
| Metrics Server | 실시간 자원 상태 |

Kubernetes 운영에서는 **런타임 아키텍처가 곧 운영 구조**입니다.
