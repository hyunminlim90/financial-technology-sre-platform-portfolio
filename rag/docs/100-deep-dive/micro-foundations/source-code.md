# 소스 코드(Source Code)

> 정독: 0회

## 1. 이 기술이 무엇인가

소스 코드는:

> 사람이 읽고 작성할 수 있는 **프로그래밍 언어 형태의 원본 프로그램**

**특징:**

- 텍스트 기반
- 인간 중심 문법
- 논리와 알고리즘 표현
- 컴파일 또는 인터프리트 대상
- 시스템 동작의 원본 정의

**대표 구성:**

| 구성 요소 | 의미 |
|----------|------|
| 변수 | 데이터 저장 |
| 함수 | 동작 정의 |
| 제어문 | 실행 흐름 제어 |
| 타입 | 데이터 구조 정의 |
| 모듈 | 기능 분리 |

소스 코드는 실행 파일의 **"원본 논리"** 입니다.

---

## 2. 시스템 어디에서 등장하는가

소스 코드는 소프트웨어 생명주기 전체의 **시작점**입니다.

| 영역 | 역할 |
|------|------|
| 설계 | 논리 구현 |
| 컴파일 | 중간 코드 생성 |
| 빌드 시스템 | 패키징 |
| 런타임 | 실행 대상 |
| 테스트 | 검증 대상 |
| 배포 | 실행 바이너리 생성 |
| 운영 | 장애 분석 기준 |

**모든 실행 시스템은 결국 소스 코드에서 시작됩니다.**

---

## 3. 어떤 자원(CPU/Memory/Network/Disk)에 가장 영향이 큰가

소스 코드 자체는 텍스트 파일이므로 직접 하드웨어를 사용하지 않습니다. 하지만 **소스 코드 구조가 최종 런타임 자원 사용량을 결정**합니다.

### CPU

알고리즘 복잡도, 반복문 구조, 병렬 처리, 스레드 모델 등이 CPU 사용량을 결정합니다.

### Memory

소스 코드가 객체 생성 방식, 메모리 점유 구조, 캐시 활용, 데이터 구조를 결정합니다.

### Disk

파일 I/O 방식, 버퍼링 전략, 로그 구조 등을 결정합니다.

### Network

프로토콜 구조, 직렬화 방식, 연결 관리 등을 정의합니다.

---

## 4. 왜 중요한가

소스 코드는 시스템의 동작 방식, 성능 특성, 안정성, 보안성, 확장성을 결정합니다.

운영 중 발생하는 대부분의 문제는 결국 **소스 코드 수준의 논리와 연결**됩니다.

| 문제 | 원인 |
|------|------|
| Memory Leak | 객체 해제 실패 |
| CPU Spike | 비효율 루프 |
| Deadlock | 동기화 오류 |
| 장애 전파 | 잘못된 의존성 |
| 데이터 손상 | 트랜잭션 오류 |

---

## 5. 실제 장애와 어떤 관련이 있는가

소스 코드와 장애의 관계는 매우 직접적입니다.

| 장애 | 코드 원인 |
|------|----------|
| OOM | 객체 과다 생성 |
| FD 고갈 | close 누락 |
| Race Condition | 동시성 제어 실패 |
| Infinite Loop | 종료 조건 오류 |
| 장애 전파 | 예외 처리 실패 |
| 성능 저하 | 비효율 알고리즘 |

> 운영 장애는 대부분 **"실행 중인 소스 코드의 결과"** 입니다.

## 6. 핵심 메커니즘

### (1) 정적 텍스트 구조

소스 코드는 디스크 위의 정적 파일입니다.

**특징:** 실행되지 않은 상태, 단순 문자 데이터, UTF 계열 인코딩, 파일 시스템 객체

대표 확장자: `.c` `.cpp` `.py` `.java` `.go`

### (2) 컴파일/해석 대상

소스 코드는 직접 실행되지 않고 중간 단계를 거칩니다.

```
소스 코드 → 컴파일/해석 → 실행 코드 → CPU 실행
```

| 방식 | 특징 |
|------|------|
| Compiler | 사전 변환 |
| Interpreter | 실시간 해석 |
| Hybrid VM | 중간 코드 실행 |

### (3) 논리 → 런타임 구조 변환

소스 코드의 구조는 런타임에서 실제 메모리 구조로 변환됩니다.

| 소스 코드 요소 | 런타임 변환 |
|--------------|-----------|
| 변수 | 메모리 영역 |
| 함수 | 호출 프레임 |
| 객체 | Heap 데이터 |
| 스레드 코드 | CPU 실행 흐름 |

**정적 텍스트가 동적 실행 상태로 변환됩니다.**

### (4) 시스템 호출 연결

소스 코드는 결국 OS 자원을 사용합니다. 파일 열기, 네트워크 송신, 메모리 할당, 스레드 생성 같은 동작은 최종적으로:

```
System Call → Kernel → Hardware
```

흐름으로 연결됩니다.

### (5) 유지보수와 변경의 기준점

소스 코드는 디버깅, 테스트, 배포, 장애 분석, 성능 최적화의 기준점입니다.

운영 중 분석도 결국 **"어떤 코드가 실행되었는가"** 를 추적하는 과정입니다.

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

| 영역 | 예시 |
|------|------|
| 파일 시스템 | source tree |
| 프로세스 실행 | ELF/Binary |
| System Call | strace |
| 메모리 매핑 | /proc |

### Runtime

소스 코드가 런타임 구조로 변환됩니다.

| 영역 | 의미 |
|------|------|
| Heap | 객체 상태 |
| Stack | 함수 호출 |
| Thread | 실행 흐름 |
| GC | 메모리 회수 |
| JIT/Compiler | 실행 최적화 |

### Kubernetes

K8s에서는 소스 코드 결과물이 컨테이너로 배포됩니다.

| 대상 | 의미 |
|------|------|
| Container Image | 빌드 결과 |
| Pod | 실행 인스턴스 |
| CPU/Memory Limit | 코드 실행 영향 |
| Logs | 런타임 결과 |
| Metrics | 코드 성능 결과 |
