# 프로세스 런타임 환경 (Process Runtime Environment)

> 정독: 0회

## 1. 이 기술이 무엇인가

프로세스 런타임 환경(Process Runtime Environment)은:

> 실행 파일이 운영체제에 의해 메모리에 적재된 후 실제로 실행되고 있는 상태의 전체 실행 환경

핵심적으로는 다음 두 가지의 결합입니다.

```
프로세스 주소 공간
+
CPU 실행 상태 (Context)
```

프로그램이 디스크에 저장된 실행 파일 상태일 때와 달리, 다음이 모두 활성화된 상태입니다.

- 메모리
- 레지스터
- 스레드
- 파일 디스크립터
- 가상 주소 공간

---

## 2. 시스템 어디에서 등장하는가

프로세스 런타임 환경은 실행 단계에서 등장합니다.

```
소스 프로그램
↓
컴파일
↓
실행 파일
↓
로더 (Loader)
↓
프로세스 생성
↓
프로세스 런타임 환경 생성
↓
CPU 실행
```

즉, **빌드 이후 / 실행 직전**부터 등장합니다.

---

## 3. 어떤 자원에 가장 영향이 큰가

가장 직접적인 영향은 **CPU**와 **Memory**입니다.

### CPU

| 보관 대상 | 설명 |
|-----------|------|
| 프로그램 카운터 (PC) | 현재 실행 위치 |
| 범용 레지스터 | 연산 데이터 |
| 플래그 레지스터 | 상태 비트 |
| 스택 포인터 | 스택 위치 |

### Memory

| 구성 영역 | 설명 |
|-----------|------|
| 코드 영역 | 기계어 명령 |
| 데이터 영역 | 전역/정적 변수 |
| 힙 | 동적 할당 메모리 |
| 스택 | 지역 변수 / 함수 호출 |
| 메모리 매핑 영역 | 공유 라이브러리 등 |

> Network와 Disk는 프로세스가 사용하는 외부 자원이며, 런타임 환경 자체의 핵심은 CPU와 Memory입니다.

---

## 4. 왜 중요한가

모든 프로그램 장애와 성능 문제는 결국 런타임 환경에서 발생합니다.

컴파일 결과가 아무리 정상이어도 다음이 발생하면 프로그램은 정상 동작하지 못합니다.

- 메모리 부족
- 스택 오버플로우
- 힙 단편화
- CPU 과부하

또한 운영체제는 프로세스 격리, 메모리 보호, CPU 스케줄링을 **런타임 환경 단위**로 수행합니다.

---

## 5. 실제 장애와 어떤 관련이 있는가

| 장애 유형 | 원인 | 결과 |
|-----------|------|------|
| 메모리 부족 (OOM) | 힙 증가, 메모리 누수 | 프로세스 종료, OOM Killer 동작 |
| 스택 오버플로우 | 과도한 재귀, 대형 지역 변수 | Segmentation Fault, Crash |
| CPU 과부하 | 무한 루프, 비효율 연산, 락 경쟁 | CPU 100%, 응답 지연 |
| 주소 공간 오류 | 잘못된 포인터, 범위 초과 접근 | 메모리 접근 위반, 프로세스 종료 |

---

## 6. 핵심 메커니즘

> **핵심 사실:** 컴파일 시점에 결정된 비트 필드 구조가 런타임 환경에서 **실제 데이터**가 된다.

아래 선언을 예로 들면:

```c
struct Config {
    unsigned int mode : 3;
    unsigned int flag : 1;
};
```

컴파일 과정에서 비트 배치, 정렬, 패딩이 결정됩니다.

프로세스가 실행되면 다음 순서로 진행됩니다.

```
실행 파일
↓
메모리 적재
↓
실제 주소 할당
↓
비트 필드 데이터 생성
```

CPU 동작 과정:

```
메모리 주소 접근
↓
워드 읽기
↓
레지스터 적재
↓
Mask 연산
↓
Shift 연산
↓
비트 필드 값 추출
```

정리하면:

| 단계 | 의미 |
|------|------|
| 컴파일 단계 | 비트 구조 설계 |
| 런타임 단계 | 설계된 구조 사용 |

## 7. Linux / Runtime / K8s에서 어디서 관측되는가

### Linux

```bash
# 프로세스 확인
ps -ef
top
htop

# 메모리 맵 확인
cat /proc/<pid>/maps

# 프로세스 상태 확인
cat /proc/<pid>/status

# 열린 파일 확인
lsof -p <pid>

# 메모리 사용량 확인
pmap <pid>
```

### Runtime

관측 대상: Heap, Stack, Thread, CPU Context, Virtual Memory

대표 도구: Debugger, Profiler, Memory Analyzer, Tracing Tool

### Kubernetes

```bash
# 컨테이너 내부 프로세스 확인
kubectl exec -it pod -- ps -ef

# 메모리 확인
kubectl top pod
```

프로세스 관점의 구조:

```
Container
↓
Process Runtime Environment
↓
Thread
```
